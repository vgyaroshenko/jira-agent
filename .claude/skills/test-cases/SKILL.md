Якщо повертає значення — використовуй. Інакше — за заголовком: і/ї/є/ґ → UA, ё/ы/ъ/э → RU, інше → EN.

## Крок 2 — QA-аналіз (обов'язковий, до генерації)

Розбий функціональність на **тестові області** і для кожної явно виписати:

### 2.1 Визнач тестові області → сьюти

Запитай себе: які незалежні частини функціональності потрібно перевірити? Кожна частина — окремий сьют (S1, S2, ...).

Приклади областей: налаштування адмін-панелі, відображення на фронті, бізнес-логіка, граничні значення, API/бек, авторизація, UI-стани, email-нотифікації тощо.

### 2.2 Для кожного сьюту виписати кейси трьох типів

| Тип | Питання для пошуку |
|---|---|
| ✅ Позитивні | Що має працювати в ідеальних умовах? |
| ❌ Негативні | Що відбувається при некоректних даних, помилках, відсутності прав? |
| ⚠️ Граничні/edge | Що на межах (0, мінімум, максимум, порожньо, одночасно)? Що якщо змінити стан в процесі? |

**Мінімум:** 1 негативний + 1 граничний на кожен сьют.

### 2.3 Перевірка покриття вимог

Пройди по кожному пункту опису та кожному AC:
- [ ] Кожен пункт опису → є тест-кейс
- [ ] "(опционально)", вкл/викл, налаштування → **окремі** кейси для кожного стану
- [ ] Кожен AC → є тест-кейс

Виведи короткий план: кількість сьютів, приблизна кількість кейсів, частка негативних (ціль ≥ 20%).

## Крок 3 — Запитати куди публікувати

Використай `AskUserQuestion` з двома варіантами:
- "Опублікувати як коментар до задачі" — markdown-таблиця одразу в Jira, потім копіюй з Jira у Google Sheets
- "Створити документ" — людиночитаємий файл `test-cases/ISSUE_KEY.md` для перегляду та зберігання

**Не генеруй тест-кейси до отримання відповіді.**

---

## Крок 4 — Згенерувати тест-кейси

### Варіант 1 — markdown-таблиця (для коментаря → Google Sheets)

Markdown-таблиця з `\n` у Steps (буквальні символи, код конвертує при відправці в Jira). Якщо є сьюти — 5 колонок, інакше 4:

```
| Suite | Case | Description | Steps | Priority |
|---|---|---|---|---|
| S1 — Назва сьюту | TC-001 — Назва | Передумови | 1. Крок\n2. Крок\nОР: результат | High |
```

Після публікації в Jira: відкрий коментар в браузері → виділи таблицю → скопіюй → встав у Google Sheets.

### Варіант 2 — людиночитаємий формат (для файлу)

```
## S1 — Назва сьюту

### TC-001 — Назва

Опис: Передумови
Пріоритет: High

Кроки:
1. Крок
ОР: результат
```

В кінці — блок **Рекомендації щодо тестування** (3–7 пунктів).

Priority: `High` — критичний функціонал, `Medium` — основні сценарії, `Low` — граничні та негативні.

## Крок 5 — Виконати дію

**Варіант 1** — опублікуй коментарем:
```bash
python main.py comment $ARGUMENTS << 'EOF'
тест-кейси у markdown-форматі...
EOF
```

**Варіант 2** — запиши у `test-cases/$ARGUMENTS.md` (перезаписуй якщо існує), повідом шлях. Публікація пізніше:
```bash
# як є (людиночитаємий):
python main.py publish-tests $ARGUMENTS
# або сконвертувати у таблицю перед публікацією:
python main.py publish-tests $ARGUMENTS --convert
```

## Крок 6 — Самоперевірка після генерації

Перевір і повідом:
- Загальна кількість тест-кейсів
- Кількість та % негативних (якщо < 20% — додай)
- Кількість та % граничних/edge
- Чи є непокриті пункти опису або AC
