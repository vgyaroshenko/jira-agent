Формування тезисного звіту про виконану за день роботу QA. Запускай проактивно (без явної команди), коли користувач пише щось на кшталт «все на сьогодні», «все на сегодня», «на сьогодні все», «закінчив на сьогодні», «рабочий день закончен», «робочий день закінчено», «day is done», «done for today», а також будь-які прощальні фрази наприкінці розмови — «пока», «до завтра», «хорошего вечера», «гарного вечора», «на сьогодні все, до завтра», «bye», «see you tomorrow», «good evening/night» тощо — або аргументи: $ARGUMENTS.

Виконуй суворо по кроках.

## Крок 1 — Розпізнай тригер

Тригер — будь-яка фраза користувача про завершення робочого дня **або звичайне прощання** наприкінці розмови (укр/рос/англ: «все на сьогодні», «пока», «до завтра», «хорошего вечера», «bye», «good night» тощо, приклади вище). Якщо розпізнано — переходь до Кроку 2.

## Крок 2 — Визнач проекти з .env і запитай проект

Прочитай доступні проекти:

```bash
grep JIRA_PROJECT_KEY .env
```

Використай `AskUserQuestion` (як у флоу `/bug-report`) — користувач **обирає** проект кнопкою, а не вводить руками:
- Якщо проектів ≤ 4 — виведи всі як варіанти
- Якщо проектів > 4 — виведи 4 найбільш вірогідні (проекти, що вже згадувались у поточній розмові — першими; далі за порядком з .env), решта доступна через вбудований варіант "Other" (користувач вписує ключ сам)

Питання: "На якому проекті закінчуєш роботу сьогодні?"

## Крок 3 — Запитай перелік справ

Після вибору проекту — окремим звичайним текстовим повідомленням запитай:

"Що встиг зробити сьогодні по проекту <PROJECT>?"

**Не використовуй `AskUserQuestion`** для цього кроку — перелік справ довільний, користувач відповідає вільним текстом (час — за бажанням, вказує сам).

## Крок 4 — Зачекай відповідь користувача

Не генеруй звіт, поки не отримав від користувача перелік справ. Час на активності, якщо вказаний користувачем — бери як є, не додавай і не вигадуй свій.

Якщо користувач згадав номер задачі або посилання на Jira (наприклад CCW-1827) — **не вставляй номер задачі у звіт**. Замість цього:

```bash
python main.py fetch CCW-1827
```

Візьми TITLE задачі і перефразуй його своїми словами (коротко, по суті) замість голого номера.

## Крок 5 — Сформуй звіт одним реченням на 2 мовами

Перетвори перелік користувача на **один суцільний абзац-речення** (без буллетів, без переносів рядків — цільова програма не бачить нові рядки), професійною QA-мовою, англійською **і** українською:

- Не просто перелічуй пункти через кому — пов'язуй їх природними сполучниками та короткими уточненнями мети/контексту (наприклад "to validate functional stability after recent updates", "to ensure the fixes work as expected"), як пише досвідчений QA у звіті
- **Не вигадуй** нових активностей, яких користувач не називав
- **Не вигадуй** конкретних фактів і цифр (кількість багів, доменів, тест-кейсів тощо), яких не було в переліку користувача — використовуй ті, що назвав користувач, як є. Загальні уточнення мети (без нових фактів) — дозволені і бажані
- Стислість: одне змістовне речення, без води

**Приклади формулювань** (розширюй за змістом, не копіюй дослівно):

| Що сказав користувач | EN | UA |
|---|---|---|
| дейлі / daily | Participation in the daily team meeting | Участь у щоденній команднiй зустрічі |
| ретест / retest багов | Retesting of fixed bug reports | Повторне тестування виправлених багів |
| функциональное тестирование | Functional testing of new features | Функціональне тестування нового функціоналу |
| нефункциональное тестирование | Non-functional testing (UX, compatibility, performance) | Нефункціональне тестування (UX, сумісність, продуктивність) |
| регресс / регрессионное тестирование | Regression testing of key scenarios | Регресійне тестування ключових сценаріїв |
| заводил баги / баг-репорты | Publication of valid bug reports | Публікація валідних баг-репортів |
| коммуникация с командой | Communication with the team | Комунікація з командою |
| тест-кейсы / написание тест-кейсов | Preparation of test cases for new functionality | Підготовка тест-кейсів для нового функціоналу |

Формат виводу:

```
**EN**
<PROJECT>: One-sentence report in English.

**UA**
<PROJECT>: Одне речення звіту українською.
```

## Крок 6 — Покажи звіт

Виведи готовий звіт користувачу в чаті обома мовами. Нічого нікуди не публікуй і не зберігай — тільки за окремим проханням.

## Крок 7 — Запитай про наступний проект

Одразу після звіту запитай: "Потрібен ще один репорт по іншому проєкту?"

- Якщо користувач одразу відповідає переліком справ (без явного проекту) — це також означає "так", але **проект все одно невідомий**: обов'язково спочатку запитай, до якого проекту належить цей перелік (Крок 2), і лише потім формуй звіт (Крок 5-6). Не намагайся вгадати проект і не питай про щось інше замість цього.
- Якщо так (з проектом) — повертайся до **Кроку 2** (вибір проекту, вже обрані сьогодні проекти можна не пропонувати повторно) і повтори Кроки 2-7 для наступного проекту
- Якщо ні — завершуй (просте прощання, без повторних запитань)
